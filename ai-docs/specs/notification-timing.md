# 通知タイミングの学習 (#24)

通知の運用開始から28日後に、調整可能な危険通知 (`risk`) の送信時間帯を学習する。本人の指定した着手時刻、朝夕のダイジェスト、24時間・3時間前の安全網、致命通知は動かさない。

## 観測

- `notifications.status = sent` の実送信時刻 `payload.sentAt` と `sessions.kind = actual` の開始時刻を使う。確認待ち (`needs_review`) の作業記録は除く。
- 学習するのは対象課題を持つ `risk` 通知のうち、可変の危険通知 (`dedupeKey = risk:<課題ID>:<連番>`) のみ。同じ `kind = risk` でも、24時間前の安全網 (`dedupeKey = due:...`) は除く。固定時刻の通知やダイジェストは異なる状況で送るため、同じ群に混ぜない。保留・まとめ元の行も実送信ではないので除く。
- 実送信から30分以内（両端を含む）に、その課題の作業開始が記録されたら成功とする。作業開始は直前の適合通知1件だけに帰属させ、ひとつの通知への成功も最大1回にする。
- 30分の観測窓が閉じるまでは成功・不成功とも加算しない。古い時刻への修正や削除も次の再計画で反映するため、学習済み集計を別途保存しない。
- 運用開始は全種別で最初の実送信時刻。28日経っていない、または観測がない場合は従来どおり先の切れ目から選ぶ。

この指標は操作記録上の代理指標であり、通知の因果効果を表すものではない。記録のない作業もあり、不成功を「通知を無視した」と解釈しない。

## 推定と候補選択

JST の0–4時、4–8時、8–12時、12–16時、16–20時、20–24時の6群で、Beta(1, 1) の事前分布へ成功・不成功を足す。各観測の重みは28日で半減し、日付が変わるまで減衰量は固定する。少ない実績では事前分布の影響を保ち、未観測の時間帯も探索する。

各群から Beta 分布の確率を1回ずつ引く Thompson sampling で、既存の予定表から作った安全な切れ目を順位付けする。候補を新しい時刻へずらすことはない。本人が着手時刻を指定している課題は、危険通知も従来どおり先の切れ目から選ぶ。3時間間隔・24時間最大3件・着手限界・締切3時間前までという既存制約を維持する。学習で選んだ通知も最後に時系列へ並べる。

乱数は課題・締切・次の通知番号・JST日付から固定seedを作る。履歴や候補が変わらないのに、再計画のたびに推薦を入れ替えない。時刻指定の通知と安全網は学習の関数へ渡さない。

## 確認

純粋関数で28日境界、30分境界、対象課題の照合、重複credit、未成熟観測、実送信以外の除外、減衰、決定性、候補・上限・最短間隔の保存を検証する。

本番DBの確認は読み取りのみ。実測件数や課題名などの個人データはこの公開リポジトリへ記録しない。
