# 保留解除まとめの原子的な作成 (#63)

## 不具合と期待する動作

通常状態へ戻ったとき、複数のdeferred通知を「保留 N件」にまとめる。旧処理では、同時に走ったdispatchが同じ元通知を読み、別々のまとめをINSERTして二重に送信できた。また、まとめINSERT後に元通知の更新が失敗すると、まとめと元通知が両方送信可能な状態で残った。

同じ元通知を重複するまとめへ入れない。作成したまとめと元通知のmerged/mergedInto更新は同時に確定し、失敗時は両方戻す。単独通知や既存ダイジェストの保留解除、期限切れの破棄、メモ抑止、最終送信時の条件付きclaimは従来どおりとする。毎分cronの頻度は変更しない。

## 保存規則

1. 候補となる元通知のID集合をJSON配列にし、json_eachを使う。IDを個別bindへ展開しないため、100件を超える集合でもD1の100変数制限内に収まる。
2. INSERT SELECTで、候補全件が現在も存在し、すべてdeferredである場合だけまとめを1件作る。countは候補IDで限定する。
3. 同じbatchの次の文で、自身のまとめIDが存在する場合だけ、その集合のdeferred行をmergedにし、payload.mergedIntoへまとめIDを保存する。他のpayload属性は維持する。
4. D1 batchの原子性により、確認・まとめ作成・元通知の更新の途中へ別要求を割り込ませない。先行した要求が取得済みの集合では、後続要求はまとめを作らず元行も変更しない。
5. 候補の一部が取得済み・skipped・削除済みの場合は、古い集合のまま本文を作らない。残りはdeferredに保ち、次のcronが最新の集合で解除する。競合によって残りの送信が次回へ遅れる場合はあるが、通知は捨てない。
6. どちらかのSQLが失敗した場合はbatch全体をrollbackする。まとめだけ・mergedだけを残さない。文面は従来の先頭5件＋「ほかN件」を維持する。

新しいテーブル・migration・永続ロックは追加しない。

## 検証

実SQLiteで、修正前に同時dispatchのまとめ2件・送信2回を再現。修正後は6ケースを通す。

- 同時dispatchでもまとめとFCM送信が各1件。
- 一方をbatch直前で待たせ、他方の作成・送信後に再開しても重複しない。
- 元通知の一部がskipped/削除になったときは古いまとめを作らず、残りは次cronで救済する（2ケース）。
- 126件でもbind制限を超えず、本文は5件と「ほか121件」。
- SQLite triggerで、まとめINSERT後の元通知UPDATEを失敗させ、まとめが残らず元行もdeferredに戻ること、次cronで回復することを確認する。

テスト用D1ラッパーはbatch内SQLを同期に連続実行し、同一SQLite接続で別PromiseのBEGINが割り込まないようにする。待機点はBEGIN前に維持する。これはD1のbatch原子性に合わせるためのテスト補助変更で、本番の接続方式は変更しない。

FCMの送信境界だけをmockし、外部fetchは禁止する。全441テスト成功。実装会話を渡さない別担当によるレビューでも再現可能な問題は見つからなかった。本番DB変更、実通知、デプロイは行わない。
