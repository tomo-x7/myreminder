# Cron の CPU 使用量とログ (#59)

## 調査根拠

11/11〜13 JSTのWorkers ObservabilityでCPU超過は717件（58/583/76）、すべて毎分のscheduledイベントだった。失敗はcpuTimeMs=10。旧版でも146件あり、毎時0分以外にも連続失敗するため、HTTPアクセスや毎時のプランナーだけでは説明できない。個別関数のCPU支配率はログだけでは特定していない。

## 通常回の処理を減らす

- cron一回につきDbを一つ作って各ステップで共有する。全テーブルのrelational metadataを毎回組み立てるschemaオプションは、本体でdb.queryを使用しないため渡さない。
- dispatchの最初に、期限到来のpendingまたはdeferredの存在を最大1行だけ調べる。両方がなければ宛先・設定・有効状態・予定を読まず終了する。未来のpendingは変更しない。
- deferredだけの回は保留解除へ進める。期限到来の通知がなくても、省略してはいけない。既存の重複排除、睡眠・作業中の保留、上限まとめ、メモ抑止、HTTPのテスト送信を維持する。
- cronの通常ステップは設定取得のPromiseを実行内で共有する。作業がなければ作業確認ステップは設定を要求しない。HTTPや次のcronには持ち越さない。取得失敗はキャッシュを解除し、次のステップで再試行できる。毎時の再計画サービス内部の設定取得は従来どおり独立する。
- getSettingsはアプリ設定6キーだけを取得する。FCMアクセストークンや日次集計マーカー等、同じテーブルの無関係な値はJSONデコード・検証しない。
- 状態の読み取りでuser_statusの初期化INSERTを発行しない。未保存なら通常として扱い、変更時は既存upsertで作る。
- cronの毎分実行、各ステップのtry/catch、作業確認→毎時のシリーズ生成/再計画→送信→日次集計の順序は変えない。

## 独立した再検証

追加の2担当が実装会話なしでレビューし、SQLiteで13ケースを確認した。期限の1ms前とちょうど、deferred単独、睡眠終了、宛先なし、onlyIdsと空配列、pendingの同時送信、失敗後再送、設定の並行取得・非同期失敗後の再試行、HTTPと次実行での設定/状態の鮮度、状態行未作成からの変更を含む。全435テストとworker型チェックが成功した。今回の差分による不具合は確認していない。

複数deferredの同時解除でまとめが二重送信される既存不具合は、旧mainでも同じ失敗を再現した。今回の回帰とは分けて #63 に記録した。毎分の頻度は本人の判断で維持する。

## 検証と限界

SQLite/D1ラッパーで、作業・通知・保留なし、日次集計前、毎時0分以外のcronを検証。設定再取得の境界、失敗後の再試行、未来の通知の保持、状態未保存、無関係なJSONを読み込まないことも確認する。既存の保留単独・上限まとめ再構成・メモ抑止テストも通す。

同じローカルSQLite、ダミーFCM設定、宛先1件、作業・通知なし、12:01 JSTで旧mainと変更後を比較した。100回×4組の通常回で、D1操作は12→3回（75%減）。ウォーム側のローカルCPUは約0.74→0.22ms/回だった。外部通信は例外に置換して禁止した。これはローカルNodeの参考値であり、Cloudflare本番のCPUや10ms以内の完走保証ではない。デプロイ後はWorkers AnalyticsのCPU超過件数・CPU分布で効果を確認する。

本番DB・設定の変更、実通知、デプロイはこの作業では行わない。

## 自動実行ログの抑制

Workers Logs に毎分出る `* * * * *` は Cron のスケジュール文字列を持つ自動 invocation log。Cron の頻度や処理は変えず、`worker/wrangler.jsonc` の `observability.logs.invocation_logs` を `false` にして、この自動ログを無効にする。HTTP リクエストを含む自動 invocation log 全体が対象となる。

`observability.enabled`、`observability.logs.enabled` は `true`、サンプリング率は `1` を維持する。アプリが明示的に出す `console.error` / `console.warn` などは引き続き収集する。障害調査に必要なエラーログを削除したり、全ログを無効化したりしない。

この設定により、自動 invocation log に含まれる各実行の結果・所要時間などの履歴は Workers Logs に新たに保存されなくなる。既存ログの削除操作ではなく、反映後の自動ログ生成を止める変更である。CPU 時間・実行回数・エラー率などの集計は Workers Analytics で引き続き確認する。ログの抑制だけで CPU 超過が解決したとは判断せず、処理の改善は別途計測する。

同梱 Wrangler の `config-schema.json` は `observability.logs.invocation_logs` を boolean と定義し、`false` で invocation logs を無効化すると説明している。ローカル設定の変更だけでは本番に反映されず、マージ後のデプロイで有効になる。
