## 0. ゴール

**締切駆動で動く僕が、課題をすっぽかさず、徹夜もしない。課題にかける時間はなるべく少なく。**

これを壊す失敗パターン(ヒアリング結果):

| 失敗 | 対策の柱 |
|---|---|
| 締切の勘違い・見落とし | 登録時に締切を曜日+相対表記で確認させる / 取り込み元がある場合は締切の変更を検知 |
| 知ってたけど忘れる | 登録を速くして必ず入れる + 朝のダイジェスト + 着手時刻の通知 |
| 着手が遅れてギリギリ→徹夜 | 正直な着手デッドライン / 実績から見積もりを較正 / 睡眠時間には作業を入れない |
| (おまけ)やったのに出してない | 「完了」と「提出済み」を分ける / 提出確認 / Classroom の提出状態を取り込む |

## 1. 性格の読み取り(仮説。違ったら直して)

| 読み取り | 根拠 | 設計への反映 |
|---|---|---|
| 締切が唯一のエンジン。遠い締切は存在しないのと同じ | 本人申告 | 遠い締切を「残り日数」ではなく「残りの**空き時間**」で見せて近く感じさせる |
| 全部締切駆動。ただし余裕があるときは前倒しする | 本人申告 | すきま時間タスクのような別枠は作らない。余裕があるときのために「余裕リスト」を用意する |
| 嘘の締切は見抜いて無視する(合理的・エンジニア気質) | 技術選定の書き方、テスト=負債という判断 | 偽の早め締切は作らない。着手デッドラインは**計算根拠を見せる**本物の制約にする |
| 早く終わらせたいわけではなく、最小の労力で落とさないのが目的 | 「課題に割く時間を最小に」 | 「早くやれ」とは言わない。ジャストインタイム+安全マージン(ALAP) |
| 見積もりが楽観的 | 着手遅れ→徹夜 | 実績から見積もりを較正する(§3.4) |
| 通知は無視しないが集中を削がれる | 本人申告 | 通知をまとめる、1日の上限、切れ目に送る、Discord 風のステータスで抑制 |
| 仕組みづくりの手間は嫌うが、件数が少ないので登録の手間は惜しまない。ただし重複などのノイズは嫌う | 本人申告 | **手動登録が主役**。自動取り込みは承認制にする |

環境: メインのスマホは Android。PC は Linux(CachyOS / fish)。pnpm、biome、Tailwind を使う。

## 2. 心理・行動科学の設計原則

詳細と出典は [research/behavior.md](research/behavior.md)。根拠の強さ: ◎ 頑健 / ○ 中程度 / △ 弱い・設計上の選択。

### 2.1 枠組み: 時間的動機づけ理論(TMT)

`動機 = (期待 × 価値) / (1 + 衝動性 × 遅延)`(Steel 2007)

先延ばしの要因を整理する枠組みとして使う(式そのものは検証された法則ではない)。

| 項 | 意味 | このアプリで動かすレバー |
|---|---|---|
| 期待 | できそうか | 小さく具体的な最初の一歩。過去の実績で「このくらいで終わる」を見せる |
| 価値 | やる価値 | (あまりいじらない) |
| 遅延 | 報酬までの遠さ | 締切を近く感じさせる表示(日数、今週/来週、残り空き時間) |
| 衝動性 | 目先に流される度合い | 通知をまとめる、通知からワンタップで「作業中」にする、着手の手間を減らす |

### 2.2 採用する仕掛け

| # | 仕掛け | 根拠 | 中身 |
|---|---|---|---|
| 1 | 正直な着手デッドライン | 本人の性格+「締切そのものは変えない」 | 締切から逆算して「この時刻までに始めないと徹夜確定」を、根拠つきで出す。偽の締切は作らない |
| 2 | 時間の見せ方 | ○ Lewis & Oyserman 2015 / Tu & Soman 2014 | `10/14(火) 23:59 ・ 3日後 ・ 今週`。さらに「残り空き 4.5h / 必要 3h」 |
| 3 | 実装意図(いつやる?) | ○〜◎ d = 0.27〜0.66 | 登録時に「いつ始める?」をワンタップで決める(AI が提案する空き枠 / 今日の夜 / 明日)。その時刻に合図を1回送る |
| 4 | 後回しには時刻を決めさせる | ◎ 現在バイアス(O'Donoghue & Rabin) | 曖昧なスヌーズは置かない。「いつに回す?」で新しい時刻を選ばせ、再計画の結果(例: 木曜に 2h 必要になる)を事実として見せる |
| 5 | 見積もりは自分の実績から | ◎ 計画錯誤 / ○ 参照クラス予測 | 見積もりの入力欄に「直近の演習: 45分, 70分, 50分」を出す。計画には実績から学習した P80 を使う(§3.4) |
| 6 | 通知をまとめる・上限・繰り返さない | ○ Fitz 2019 / Ancker 2017 | 朝・夜のダイジェストが基本。致命以外の個別通知は1日3件まで。同じ文面を繰り返さない |
| 7 | 通知は切れ目に送る | ○ 割り込みの研究 | 空き枠の始まり(授業が終わった直後など)に送る。授業中・作業中・睡眠中は送らない |
| 8 | 進捗の見せ方 | △〜○ 目標勾配 / Koo & Fishbach 2012 | 前半は「やった分」、後半は「残り」を見せる |
| 9 | 週の始まりに見通し | △ フレッシュスタート効果 | 月曜の朝と学期の始めに「今週の山場」を出す |
| 10 | 最初の一歩 | △ 直接の検証なし。オフシャンキナ効果(再開傾向)から妥当そう | 通知に「まず5分: テンプレを開いて見出しだけ書く」を添える。効くかどうかはアプリ内で測る |
| 11 | ホームは次の1件 | △ 選択過多の平均効果はほぼ0 → 好みの設計として | 今やるべき1件を大きく出す。全リストはワンタップで開ける |
| 12 | 余裕リスト | △ 構造化された先延ばし(Perry)はエッセイのみ → 設計上の選択 | 余裕のあるタスクを「今やると生み出せる余裕」順に並べる(§3.6) |

### 2.3 使わないもの(根拠が弱い・否定された)

後から「心理ハック」として足したくなっても、これらは入れない。

- 偽の早め締切、外部から等間隔の中間締切を押しつけること(Ariely & Wertenbroch 2002 は事前登録された再現で失敗。学生の実験でも、自分で決めた締切で完了率は上がらなかった)
- 「未完了だと脳が気にし続ける」という文言(ツァイガルニク効果は2025年のメタ分析で否定)
- 意志力の消耗・決断疲れを前提にした設計(36ラボの研究で d = 0.06)
- 固定の見積もり倍率(×1.5 など)。一次資料がないので、実績から学習する
- 損失フレームの煽り文句(一次資料を確認できず)。後回しの影響は事実として見せるだけ
- 罰つきのコミットメント
- ストリーク。使うなら修復・凍結を可能にし、途切れを強調しない(未決事項)
- WOOP(障害を考える問い)の必須化。セルフサービスでは効果が小さい(g ≈ 0.28)

## 3. 機能一覧

### 3.1 タスク

- 状態: `todo` → `doing` → `done`(作業完了) → `submitted`(提出済み) / `dismissed`
- 項目:
  - タイトル、科目、種類(レポート/演習/小テスト/発表準備/その他)、締切
  - 見積もり(分)と、その出どころ(AI/手入力)
  - 最小の作業単位(既定30分)、公開日時(任意。それより前は着手できない)
  - 本人が決めた着手時刻、最初の一歩、メモ
- 締切表示: `10/14(火) 23:59 ・ 3日後 ・ 今週`。`24:00` 表記は `翌日 0:00` に正規化して表示し、日付の取り違えを防ぐ
- 締切が変わったら通知し、履歴に残す
- `done` のまま `submitted` にならない場合は「提出した?」を確認する

### 3.2 手動登録(主役)

ここの速さと正確さに一番力を入れる。

- **自然文1行** → AI が解析 → 確認カード → 保存
  - 例: `情報倫理 来週月曜の授業前までにレポート2000字`
  - 時間割を AI に渡すので、「授業前」は授業の開始時刻に解決される
  - 確認カードでは、締切を `10/20(月) 10:40 ・ 9日後 ・ 来週` のように必ず曜日+相対で見せる(勘違い対策の要)
  - 確認カードでそのまま「いつ始める?」も決める(§2.2-3)
- **告知文の貼り付け** → AI が複数のタスクを抽出 → まとめて確認。ポータルのお知らせやメールの本文をそのまま貼る用途
- **Android の共有メニューから PWA に送る**(Web Share Target)。テキストや URL を共有するだけで、上の貼り付けと同じ流れに入る
- (後回し)スライドの写真 → 視覚モデルで抽出

### 3.3 時間割・予定・睡眠・作業上限

- 時間割: 曜日×時限で登録。学期の期間つき
- 単発の予定(バイトなど)
- 睡眠時間帯(既定 1:00–8:00 など)
- **1日の作業上限**(平日/休日)。計画はこの範囲でしか組まない。最小の労力で済ませたい本人の方針を数値にしたもの
- 以上から「使える時間」を作り、計画の基準にする

### 3.4 見積もり(純粋関数。テスト対象)

- 初期値は AI が推定する(似たタスクの実績を few-shot で渡す)か、手入力
- 入力欄の横に、同じ種類の直近の実績を出す(参照クラス)
- 学習の仕組み(詳細は [research/algorithms.md](research/algorithms.md#見積もり計画錯誤への対策)):
  - 完了したタスクの `r = 実績 / 見積もり`。実績は作業中タイマーの合計
  - `ln r` を正規分布とみなし、正規–逆χ² で更新する(事前 μ0 = ln 1.3、σ0 = 0.5、擬似観測 2〜4件)
  - 区分は種類 × サイズ(〜1h / 1–3h / 3h〜)。データが少ない区分は全体の値に寄せる(縮小推定、k ≈ 5)。新しい実績ほど重く(半減期 15件)
  - **計画に使うのは P80** = 見積もり × exp(μ + 0.84σ)(下限は ×1.0)
- 初期状態ではかなり保守的(約2倍)になる。実績がたまるほど本人に合ってくる
- 残りの見積もりは、作業中を終えるときの「どれくらい進んだ?」(25/50/75/100%)で更新する

### 3.5 スケジューラ(純粋関数。テスト対象)

詳細と出典は [research/algorithms.md](research/algorithms.md)。

1. **使える時間**: 14日先まで。空き時間のうち1日の作業上限までを使える時間とする(睡眠時間帯は含めない → **徹夜を構造的に禁止**)
2. **締切ごとの余裕**(需要上限テスト): `s_i = 使える時間(今, d_i) − Σ{d_j ≤ d_i} 残りの P80`
   - **山場** = 余裕が最小になる締切。「11/18 の週が山場、余裕 1.5h」のように見せる
3. **具体的な配置**: EDF を締切側から逆向きに回し(ALAP / Earliest Deadline Last)、各タスクを使える時間に詰める
   - 最小の作業単位と公開日時を守る。守れない場合は EDF+修正パスで対処する(n ≤ 30 なら十分)
   - 結果として、各タスクの**着手デッドライン**(P80 で計算)と、おすすめ着手時刻(着手デッドライン − マージン)が出る
4. **間に合わない場合**(どこかの s_i < 0): Moore–Hodgson で「間に合わないタスクの数が最小になる捨て方」を出す。手を抜く・延長を頼む候補として提示する
5. **リスクレベル**(タスクごと): 着手デッドラインまでの、使える時間で測った余裕を使う。CCPM のバッファ消費率のように緑・黄・赤で見せる(§3.8)
6. 再計画のタイミング: タスクや予定の変更時と、cron の毎時処理

並び順は EDF(締切順)にする。LLF や Critical Ratio は順位が頻繁に入れ替わるので、並び順には使わない(表示用の指標にとどめる)。

### 3.6 余裕リスト(前倒し候補)

本人の要望: 余裕があるタスクも見たい。余裕があればやるので、生み出せる余裕の大きい順に並べたい。

- **対象**: 急ぐ必要がない(リスクが「余裕」の)タスク
- **並び順**: 「次の空き時間をこのタスクに使った場合」と「休んだ場合」を比べた、計画全体の改善量の大きい順
  - 空き時間の長さは、既定では次の予定までの時間(上限90分)。30/60/90分から手で選べる
  - 比較は辞書式で行う:
    1. 間に合わないタスクの数
    2. 山場の余裕
    3. 全体のストレス = 各締切の余裕を1日分の使える時間で割り、`exp(−s/τ)` を足したもの
  - 計算方法は**反実仮想の再計画**: 候補ごとにスケジューラを回し直す。n ≤ 30 なので軽い。重ければ O(n) の近似 `score(T) = Σ{d_i ≥ d_T} exp(−s_i/τ)` を使う
  - 同点の場合は「締切が早い → 残作業が多い → ID」の順で決める(開くたびに順位が入れ替わらないように)
- **表示**: 「60分やると: 山場(11/18 の週)の余裕 +60分」と、理由を1行(「まとまった時間が要るので、大きく空いている今やる価値が高い」など)
- **正直な注意書き**(本人向け): 理論上は、締切が早いものほど上に来やすい(早い締切を片付けると、それ以降のすべての締切の余裕が増えるため)。締切順と差がつくのは次の3つのとき:
  1. まとまった時間が要るタスク(将来の空き時間は細切れになりやすい)
  2. 見積もりが不確かなタスク(早く始めると読みが当たる)
  3. 山場の手前にあるタスク
- 余裕リストからやった作業を、その日の作業上限に含めるかどうかは 2-1 で詰める

### 3.7 ステータス(Discord 風・手動+自動ルール)

| ステータス | 通知の扱い | 自動で切り替わる条件 |
|---|---|---|
| 🟢 通常 | 通常どおり | — |
| 🛠 作業中: {タスク} | 致命以外は保留。タイマーで計測し、終了時に「どれくらい進んだ?」で残りを更新 | 通知の「始める」ボタン |
| 🔴 取り込み中 | 致命以外は保留 | 時間割の授業中、バイト中 |
| 🌙 おやすみ | すべて保留して朝のダイジェストにまとめる | 睡眠時間帯 |

- 手動で設定するときは期限つき(30分 / 1時間 / 今日中 / 解除するまで)
- 保留が明けたら、保留中の通知は「保留中 N件」の1通にまとめる(連続で鳴らさない)

### 3.8 通知ポリシー

**送る時刻**: 切れ目に合わせる(空き枠の始まり、授業が終わった直後、本人が決めた着手時刻)。授業中・作業中・睡眠中は、致命以外は送らない。

**定時のダイジェスト**:

- 朝: 今日やること、今週の山場、承認待ちの件数
- 夜: 今日の予定の確認(「終わった? [済] [いつに回す?]」)
- 月曜の朝: 週の見通し

**リスク別**(余裕は P80 の着手デッドラインまでの、使える時間で測る):

| リスク | 条件(目安) | 通知 |
|---|---|---|
| 余裕 | 余裕が必要時間の2倍超 | 個別通知なし。ダイジェストと余裕リストに載るだけ |
| 注意 | それ以下 | 本人が決めた着手時刻(なければおすすめ着手時刻)に1回+最初の一歩 |
| 危険 | 着手デッドラインが24h以内 | 着手デッドラインに向けて、次の切れ目ごとに。文面は毎回変える |
| 致命 | 締切3h以内で未提出 | 作業中・取り込み中でも通す(おやすみ中は設定次第)。FCM の `Urgency: high` |

**上限と例外**:

- 致命以外の個別通知は1日3件まで。超えた分はまとめる
- 承認待ちの取り込みで締切が48h以内のものは、個別に通知する(承認待ちのせいで見落とさないため)
- (Phase 4)通知ごとに「30分以内に作業を始めたか」を記録する。4週間分たまったら、時間帯ごとの Thompson sampling で送るタイミングを調整する

### 3.9 自動取り込み(承認制・段階的なおまけ)

**方針**:

- 手動登録だけで成立させる
- 自動取り込みは、作る手間が小さく、手動より楽になるものだけにする
- **取り込んだものは必ず受信箱で承認して初めてタスクになる**(重複でうざくならないように)

| 優先度 | 取り込み元 | 方式 | 得られるもの |
|---|---|---|---|
| 1 | Google Classroom | 大学アカウントの Apps Script(TS+esbuild、手動コピペ)が1時間ごとに Classroom API を叩き、スナップショットを POST する | 課題、締切、提出状態 |
| 2(任意) | WebClass | ブラウザ拡張(MV3)。ログイン中のセッションを流用して科目ページを巡回・解析する | 課題、締切 |
| — | Gmail・ポータル | 取り込まない(メールは全件見ているため)。必要なら共有メニューで手動登録 | — |

**流れ**:

1. 取り込み元が `POST /api/ingest/{source}` にスナップショット全体を送る。差分はサーバーで取るので、Apps Script は状態を持たない
2. `ingest_items` に `(source, external_id)` で upsert する。新しいものは「承認待ち」として受信箱に入る
3. 受信箱でのアクション:
   - [タスクとして追加]
   - [既存のタスクに紐付け]: 科目+正規化したタイトル+締切±1日 で重複の候補が見つかったら並べて表示し、既定のアクションをこれにする
   - [無視]: 無視したものは覚えておき、次の同期で再び出さない

**紐付け済みのアイテムが変わったとき**([提案]):

- 締切が早まった → すぐ反映して通知する(見落とすと危ない方向なので安全側に倒す)
- 締切が遅くなった、タイトルが変わった → 受信箱に「変更の提案」として出す
- Classroom で `TURNED_IN` → `submitted` を自動で付ける。`RECLAIMED_BY_STUDENT` → `todo` に戻して通知する

**WebClass の拡張を作る場合**: 既存の OSS の解析方法を参考にする([research/platform.md](research/platform.md#webclassデータパシフィック))。

### 3.10 AI(Workers AI 無料枠: 1日 10,000 neurons)

| 用途 | タイミング | 1日あたりの回数(目安) |
|---|---|---|
| 自然文1行の解析 | 登録時 | 数回 |
| 貼り付け・共有されたテキストからの複数抽出 | 登録時 | 数回 |
| 種類の判定と所要時間の初期推定(似たタスクの実績を few-shot で渡す) | 登録時 | 数回 |
| 最初の一歩の生成 | 登録時 | 数回 |
| ダイジェストの文面 | 1日1〜2回 | 2 |

- 主力: `@cf/qwen/qwen3-30b-a3b-fp8`(1回 ≈16 neurons と推定。1日 ≈600回分)
- 予備: `@cf/meta/llama-3.3-70b-instruct-fp8-fast`(JSON mode が公式ドキュメントに記載されている。1回 ≈100 neurons)
- 出力は必ず valibot で検証する。失敗したら1回だけ再試行し、だめなら予備に切り替える
- JSON mode は「条件を満たせない」エラーを返すことがあるので、エラー処理を入れる
- 日本語の品質はドキュメントに記載がない → 実際の告知文で試して選ぶ
- 通知の送信処理(cron)では AI を呼ばない。文面は登録時やダイジェストの生成時に作って保存しておく

## 4. 技術スタック

### 4.1 構成

```
                ┌──────── Cloudflare Access (Zero Trust) ─────────┐
Android PWA ──▶ │ 独自ドメイン                                      │
(FCM SW)        │  ├─ 静的アセット (web/dist, SPA フォールバック)      │
                │  └─ /api/* ──▶ Worker (Hono)                      │
Apps Script ──▶ │       /api/ingest/* は Service Token (Service Auth) │
WebClass 拡張 ─▶ │                                                   │
                └────────────────────────────────────────────────┘
                       Worker: fetch / scheduled (cron 毎分)
                         ├─ D1 (drizzle)
                         ├─ Workers AI
                         └─ FCM HTTP v1 ──▶ 端末
```

- **Worker は1つ**: Workers Static Assets で SPA を配信し、`/api/*` だけ Worker を通す(`run_worker_first: ["/api/*"]`)
  - 同じオリジンなので Access の cookie がそのまま効き、CORS も不要
  - 静的アセットへのリクエストは無料・無制限で、Worker の 10万リクエスト/日 にはカウントされない
- Apps Script と拡張は、Access の Service Token(`CF-Access-Client-Id` / `CF-Access-Client-Secret` ヘッダー)で `/api/ingest/*` に POST する。そのパスだけ別の Access アプリにし、ポリシーを Service Auth にする

### 4.2 バックエンド (`worker/`)

| 項目 | 採用 | メモ |
|---|---|---|
| ランタイム | Cloudflare Workers(無料プラン) | CPU 10ms/回、外部へのサブリクエスト 50/回 |
| フレームワーク | Hono | ルートはメソッドチェーンで書き、`AppType` を export する |
| バリデーション | valibot + `@hono/valibot-validator` | (依頼文の「validot」は valibot と解釈した) |
| DB | D1 + drizzle-orm / drizzle-kit | マイグレーションは `drizzle-kit generate` → `wrangler d1 migrations apply` |
| 定期実行 | Cron Trigger `* * * * *` を1本 | 中で分岐して、毎分の通知送信・毎時の再計画・定時のダイジェストを行う。無料枠は5本 |
| AI | Workers AI バインディング | §3.10 |
| プッシュ | FCM HTTP v1 を直接叩く | サービスアカウントの JWT(RS256)を WebCrypto か `jose` で署名して OAuth トークンを取得。トークン(1h)はモジュールスコープと D1 にキャッシュ |
| 認証 | なし(Access に任せる) | すべてのリクエストを同一ユーザーとして扱う |

エクスポートの形:

```ts
export default {
	fetch: app.fetch,
	scheduled: (event, env, ctx) => { /* 毎分の処理 */ },
} satisfies ExportedHandler<CloudflareBindings>;
```

`wrangler.jsonc` の要点:

```jsonc
{
	"name": "myreminder",
	"main": "src/index.ts",
	"workers_dev": false, // Access を迂回させない
	"preview_urls": false, // 同上(workers_dev だけでは塞がらない)
	"routes": [{ "pattern": "<独自ドメイン>", "custom_domain": true }],
	"assets": {
		"directory": "../web/dist",
		"not_found_handling": "single-page-application",
		"run_worker_first": ["/api/*"],
	},
	"triggers": { "crons": ["* * * * *"] },
	"d1_databases": [{ "binding": "DB", "database_name": "myreminder", "database_id": "..." }],
	"ai": { "binding": "AI" },
}
```

### 4.3 フロントエンド (`web/`)

| 項目 | 採用 | メモ |
|---|---|---|
| ビルド | Vite + React 19 | 既存の雛形をそのまま使う |
| API クライアント | `hc<AppType>` + TanStack Query | `worker` を workspace 依存にして `import type` する。**web の tsconfig にも `strict: true` が必要**(ないと hc の型推論が崩れる) |
| ルーティング | TanStack Router(または画面が少なければ不要) | 画面: ホーム(次の1件)/ 一覧 / 余裕リスト / 受信箱 / 時間割 / 設定 |
| スタイル | Tailwind CSS v4 | shared の biome 設定に tailwind 用の override があるため |
| PWA | Web App Manifest + 自前の Service Worker | FCM の `firebase-messaging-sw.js` と統合する。Share Target もここで |
| プッシュ | firebase JS SDK(messaging のみ) | 新しい SDK はトークン API が変わっている(`register()` 方式)ので、実装時に確認する |

**Access と Service Worker の注意点**:

- Service Worker はナビゲーションと `/api` をキャッシュしない(ネットワーク優先)
- `/cdn-cgi/*` は Service Worker で扱わない
- `/api` が 302/401/403 を返したら、ページを再読み込みして Access のログインに飛ばす
- Access のセッション期間は長め(例: 1か月)にする

### 4.4 Apps Script (`gas/`)

詳細は [research/gas.md](research/gas.md)。

- TypeScript で書き、esbuild で `dist/Code.js` にまとめる
  - `format: "iife"` + `globalName`
  - footer で、トリガーから呼ぶ関数をトップレベルに宣言する
  - target は es2019
- 型は `@types/google-apps-script`、型チェックは `tsc --noEmit`
- デプロイ: `dist/Code.js` と `appsscript.json` をエディタに手でコピペする(clasp は使わない)
- トリガーはエディタから手で作る(1時間ごと)
- 秘密情報(Service Token、送信先 URL)は Script Properties に入れる。コードにもリポジトリにも置かない
- Classroom の締切(`dueDate` + `dueTime`)は UTC なので、epoch ミリ秒にしてから送る

### 4.5 共通

- 時刻は D1 に epoch ミリ秒(integer)で保存する。日付の境界は JST(+09:00 固定、夏時間なし)で計算する
- 開発: `pnpm web dev`(Vite)と `pnpm worker dev`(wrangler)を並行で起動し、Vite の proxy で `/api` を 8787 に流す
- デプロイ: `pnpm -F web build && pnpm -F worker deploy`
- lint・フォーマット: biome(既存の shared 設定)
- テスト: vitest で `worker/src/planner/` の純粋関数(見積もり、スケジューラ、余裕リストのスコア)だけ。必要になったら取り込みの正規化と重複排除も足す。それ以外は書かない

### 4.7 データモデル(案)

| テーブル | 主な列 |
|---|---|
| `courses` | id, name, aliases(取り込み元ごとの表記揺れ), color |
| `tasks` | id, course_id, title, category, due_at, release_at?, estimate_min, estimate_source, min_block_min, status, planned_start_at(本人が決めた着手時刻), first_step, note, submitted_at, created_at, updated_at |
| `task_due_history` | task_id, old_due_at, new_due_at, changed_at, cause(manual/ingest) |
| `sessions` | id, task_id, kind(planned/actual), start_at, end_at, progress |
| `busy_blocks` | id, kind(class/job/event), weekday?, start, end, date_from?, date_to?, label |
| `ingest_items` | id, source, external_id(source との組で一意), title, course_name, due_at, url, remote_state(提出状態など), payload_json, status(pending/linked/ignored), task_id?, pending_change_json?, first_seen_at, last_seen_at |
| `user_status` | mode, task_id?, until(1行のみ) |
| `notifications` | id, task_id?, kind(digest/start/risk/critical/due_change/submit_check/evening/weekly/inbox), priority, scheduled_at, status(pending/sent/deferred/merged/skipped), payload |
| `push_tokens` | token, label, created_at, last_seen_at |
| `ai_log` | id, purpose, input_text, output_json, model, status, error(手動登録の解析のデバッグ用) |
| `settings` | key, value(睡眠時間帯、1日の作業上限、見積もりの事前分布、通知の上限、FCM トークンのキャッシュなど) |

通知の流れ:

- 再計画のたびに、未来の `notifications` を作り直す(`pending` のものだけ置き換える)
- 毎分の cron は `scheduled_at <= now AND status = pending` を取り出し、送信時点のステータスを見て、送信・保留・まとめのどれにするかを決める

### 4.8 無料枠の見積もり

| リソース | 上限 | 想定使用量 |
|---|---|---|
| Workers リクエスト | 100,000/日 | cron 1,440 + API 数百 + Apps Script 24 ≈ 2,000 |
| Cron Trigger | 5本/アカウント | 1本 |
| D1 | 読み取り 500万行/日、書き込み 10万行/日 | 誤差の範囲 |
| Workers AI | 10,000 neurons/日 | 〜1,000 |
| Access / FCM / AI Gateway | 無料 | — |

ボトルネックになりうるのは **CPU 10ms** だけ。

- FCM トークン取得時の RS256 署名: トークンをキャッシュすれば1時間に1回で済む
- 余裕リストの反実仮想の再計画: n ≤ 30 なら軽いはずだが計測する。重ければ O(n) の近似に切り替えるか、ブラウザ側で計算する

## 6. 未決事項(本人に確認したいこと)

1. **1日の作業上限**(平日/休日)の初期値。計画の基準になる。
2. **起床・就寝の時刻**、朝・夜のダイジェストを送る時刻。
3. **作業中タイマーを使う習慣が付きそうか**。見積もりの学習の前提になる。付かなそうなら、完了時に「何分かかった?」を聞く方式にする。
4. **時間割**: 手入力でよいか。大学のポータルから取り込みたいか。
5. **ゲーミフィケーション**: 調査では、ストリークは途切れたときに逆効果になるリスクがあった。既定はなしで進捗を見せるだけにする予定。欲しければ、修復できるストリークにする。
6. **独自ドメイン**: アプリを置くドメイン(Cloudflare で管理しているもの。サブドメインでよい)。
7. **WebClass のログイン方式**: 学内 ID で直接ログインするのか、SSO+MFA なのか(拡張を作る場合のみ必要)。
