### #3 2026-10-11 [提案] Worker は1つで SPA と API を同一オリジンで配信

Workers Static Assets で `web/dist` を配信し、`run_worker_first: ["/api/*"]` で API だけ Worker を通す。

### #17 2026-10-11 [提案] スケジューラと見積もりのアルゴリズム

調査結果([research/algorithms.md](research/algorithms.md))をもとに決めた。

- 並び順は EDF にする。LLF や Critical Ratio は順位が頻繁に入れ替わるので、表示用の指標にとどめる
- 締切ごとの余裕は、需要上限テストで出す。余裕が最小になる締切を「山場」として見せる
- 具体的な配置は ALAP(Earliest Deadline Last)。エスカレーションは P80 で計算した着手デッドラインで判定する
- 間に合わないときは、Moore–Hodgson で捨てる候補を出す
- 見積もりは `ln(実績/見積もり)` の正規–逆χ² 更新。種類×サイズで縮小推定し、P80 を使う
- 1日の作業上限を、計画の「使える時間」の上限にする

### #18 2026-10-11 [提案] 余裕リストのスコアは反実仮想の再計画

#15 の「生み出せる余裕」を、次のように定義した。

- 定義: 「次の空き時間をそのタスクに使った場合」と「休んだ場合」の、計画全体の改善量
- 比較は辞書式: 間に合わないタスクの数 → 山場の余裕 → 正規化したストレス
- 流体モデルでは締切が早いほど有利になる。差がつくのは、まとまった時間が要るタスク・見積もりが不確かなタスク・山場の手前にあるタスクのとき。これは本人向けに正直に表示する
- 重ければ O(n) の近似 `Σ{d_i ≥ d_T} exp(−s_i/τ)` に切り替える

### #19 2026-10-11 [提案] 取り込みの承認フローの詳細

#13(承認制)を、次のように具体化した。

- 取り込み元はスナップショット全体を送り、差分はサーバーで取る(Apps Script は状態を持たない)
- 受信箱のアクションは、追加・既存タスクへの紐付け・無視の3つ
  - 重複の候補があるときは、既定のアクションを紐付けにする
  - 無視したものは二度と出さない
- 紐付け済みのアイテムが変わったとき:
  - 締切が早まった → 即反映+通知(安全側に倒す)
  - 締切が遅くなった、タイトルが変わった → 変更の提案として受信箱に出す
  - 提出状態(TURNED_IN / RECLAIMED_BY_STUDENT)→ 自動で反映する
- 承認待ちで締切が48h以内のものは、個別に通知する

### #28 2026-10-11 [提案] 取り込みの実装で、仕様に足した細部(#21)

- 差分の決定は純粋関数 `planIngest`(`worker/src/services/ingest.ts`)。1回の select(紐付け先のタスクも join)で読み、書き込みは変わった行だけ batch。新規の insert は D1 の束縛上限(1文100個)に合わせて6行ずつ
- 重複の候補の「科目が同じ」は、科目名に加えて**別名(`courses.aliases`)**でも合わせる。Classroom のコース名(`情報倫理(月2)`)と登録した科目名の表記揺れを吸収するため
- 朝のダイジェストは、タスクがなくても受信箱の確認待ちがあれば作る(締切が48時間より先の承認待ちを見落とさないため)
- 取り込みでタスクが変わったとき(締切が早まる・提出済み・提出取り消し)だけ再計画する。承認待ちが増えるだけのときは再計画しない(朝のダイジェストの件数は毎時0分の再計画で更新される)
- 個別通知(`inbox` / `due_change`)は `priority = 1`、`dedupeKey` なし。タイトルに課題名を入れる(他の通知と同じ書き方)
- `GET /api/inbox` に、[追加] の確認カード用の `startSuggestions` と `now` を含める(承認待ちがあるときだけ計算)

### #29 2026-10-11 [提案] スライドの写真は Gemma 4 26B A4B で1回で読み、予備は Qwen3.8 27B(issue #25)

調査は [research/platform.md](research/platform.md) の「画像入力(Vision)に対応するモデル」。

- **主力: `@cf/google/gemma-4-26b-a4b-it`**
  - 画像を `messages` の `image_url`(data URI)で渡せ、`response_format: json_schema` も使える(API スキーマに明記)
  - 無料枠で使える(有料必須の一覧に入っていない)
  - 安い: 入力 9,091 / 出力 27,273 neurons/100万トークン
  - 思考は `chat_template_kwargs.enable_thinking: false` で切る(公式チュートリアルと同じ)
  - 日本語の読み取りは、Google が OCR に強いと述べ、日本語マルチモーダル評価でも悪くない程度のことしか確認できていない。**スライドの写真での実測は未確認**
- **予備: `@cf/qwen/qwen3.8-27b`**
  - 主力と同じ入力・出力の形なので、モデル名を替えるだけで済む
  - 出力が高い(290,909 neurons/100万トークン)ので、予備の1回だけにして `max_tokens` を 1500 に絞る
- **使わなかったもの**
  - `llama-3.2-11b-vision-instruct`: 初回にライセンスの `agree` を送る手間があり、JSON mode がない。画像の渡し方もモデルページとチュートリアルで食い違う
  - `llama-4-scout`・`mistral-small-3.1`: 画像の渡し方が公式のスキーマに書かれていない(未確認)
  - `llava-1.5-7b-hf`: Beta で、料金表になく、JSON 出力の仕組みもない
  - `moondream3.1`: 自由な JSON を返す仕組みが未確認
  - `gemma-3-12b-it`: モデルのページが消えている
- **2段階(書き起こし → 既存の文章の解析)にしない**
  - json_schema が使えるモデルなら1回で済み、呼び出しが増えない。壊れたときは既存と同じ再試行・予備・valibot の検証で受ける
  - 実測で読み取りが弱いと分かったら、1段目だけ画像モデルにして2段目は既存の `parseTasks` に差し替えられる(`parseImage` の中だけの変更)
- **1回のコストの推定は約 36 neurons**(入力 約2,800 + 出力 約400トークン。画像のトークン数は未確認なので、Gemma 4 の最大の予算 1120 で見積もった)
  - 無料枠 10,000 neurons/日なら約270回。文章の解析(≈16)と合わせても足りる
  - 300 neurons を超えないので、**1日あたりの回数の上限は設けない**。予備の Qwen3.8 に回ったときだけ ≈230(思考を切れなかったとき最大 ≈550)かかるが、まれ
  - 実機で1回走らせて Workers AI のダッシュボードで実測し、300 を超えるなら ai_log から数える1日の上限を足す
- **API は `POST /api/parse/image`**(multipart、フィールド `image`)
  - モデルに渡すには base64 にするので、サーバーで変換する。base64 の JSON より、アップロードが約3割小さい
  - 1.5MB を超えたら 413、JPEG・PNG・WebP 以外は 415。返す形は `/api/parse/text` と同じ。ログには画像を入れず「(画像 image/jpeg 123KB)」だけ残す
- **確認カードの扱い**
  - 写真からの結果は読み違いがありうるので、画面の上に「文字の読み違いがないか確認してください」を出す
  - 確認が必要な印(`needsReview`)は既存と同じ基準(締切を読めない・自信が低い・過去の日付など)
- **共有メニュー(Web Share Target)から画像を受ける**
  - manifest の `share_target` を POST(multipart)にし、Service Worker が受けた画像を Cache に入れて `/share?image=1` へ飛ばす。テキストだけの共有も同じ POST で届くので、Service Worker が従来の GET の形に直して飛ばす
  - **Service Worker が登録されていないと共有が動かなくなる**。この Service Worker は通知を有効にしたときに登録する(アプリを開くたびに更新する)ので、通知を有効にしていない端末では共有が使えない

### #30 2026-10-11 [提案] 週次のふりかえりの定義(#26)

- 週は活動日で数える(月曜の起床から次の月曜の起床まで、JST)。提出・完了もこの境目で週に入れる
- 徹夜 = その夜の睡眠時間帯に、確定済みの作業が合計60分以上重なった日。「徹夜なし N/M 日」の分母は、夜が明けた日だけ
- 見積もりの比率(実績 ÷ 見積もり)は、最後の確定済み記録の終了が属する週に入れ、週ごとの中央値を8週並べる
- ストリーク(連続の長さ)は作らない。遅れた提出は赤にせず事実だけを書く。前の週との比較は中立に並べるだけ
- 月曜朝のダイジェストの URL は `/review`。ホームの「先週のふりかえり」は常に出し、月曜だけ強調する
- 詳細は [specs/review.md](specs/review.md)

### #31 2026-10-11 [提案] 共有メニューは POST にして写真も受ける。Service Worker は起動時に必ず登録する(#25)

- manifest の `share_target` を POST(multipart)にし、写真を受けられるようにした。POST /share は Service Worker が受け、写真は Cache に入れて `/share?image=1`、テキストだけなら従来の GET の形に直して飛ばす
- そのため共有は Service Worker に依存する。通知をオンにしていなくても共有が動くよう、Service Worker はアプリの起動時に必ず登録する(`main.tsx`)
- 写真の読み取りは実機・本物のモデルで未確認(日本語の精度、neurons の実測)。初回のデプロイ後に確かめる
