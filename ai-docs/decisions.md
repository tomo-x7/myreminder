### #1 2026-10-11 [本人] 前提となる技術仕様

- デプロイ先は Cloudflare の無料プラン
- ログインは Cloudflare Zero Trust Access に任せる。コードではすべてのリクエストを同一ユーザーとして扱う
- Vite + React / Hono + drizzle + valibot / Hono RPC の型共有と `hc`
- テストは、必要ならバックエンドの壊れやすい箇所だけユニットテスト。なるべく書かない(この規模だと負債になる)
- プッシュ通知は FCM

### #2 2026-10-11 [提案] 「validot」は valibot と解釈

依頼文に「validot」とあったが npm に存在しない。valibot の打ち間違いとみなした。

### #3 2026-10-11 [提案] Worker は1つで SPA と API を同一オリジンで配信

Workers Static Assets で `web/dist` を配信し、`run_worker_first: ["/api/*"]` で API だけ Worker を通す。

- Access の cookie がそのまま効き、CORS が不要になる
- 静的アセットへのリクエストは無料枠のリクエスト数にカウントされない
- `workers_dev: false` と `preview_urls: false` を必ず設定する(Access を迂回させないため)

### #4 2026-10-11 [提案] 通知は「毎分の cron+`notifications` テーブル」

Durable Object の Alarm ではなく、cron を1本(`* * * * *`)にして、送信予定のテーブルを毎分見る方式にした。

- 精度は1分で十分
- 構成が単純
- 使うリクエスト数は1日 1,440 で、無料枠の 10万/日 に対して余裕がある

### #5 2026-10-11 [提案] FCM は HTTP v1 を直接叩く

firebase-admin は使わない。サービスアカウントの JWT を WebCrypto か `jose` で署名し、OAuth トークンをキャッシュする。

### #6 2026-10-11 [提案] Workers AI は qwen3-30b を主力、llama-3.3-70b を予備に

出力は valibot で検証する。日本語の品質は実際のデータで確認してから確定する。

### #7 2026-10-11 [本人] 手動登録が主役、自動取り込みは段階的なおまけ

本人の言葉: 「スクレイピングが面倒であれば、ぜんぶ手動で登録できる程度だからそれでもいいかな、その手間は惜しまない」。

- 手動登録(自然文の解析、貼り付け、共有メニュー)を MVP の中心にする
- 自動取り込みは、作る手間が小さく効果が大きいものから足す。どこで止めてもよい

### #8 2026-10-11 [本人+提案] メールは Cloudflare Email Routing ではなく Apps Script で Gmail を読む

- [本人] 大学メールは Gmail。課題がメールで直接来ることは少ない。アンケートや奨学金などの事務系タスクはポータルなどから来る。Apps Script でスクレイピングしてもいいし、手動でもいい
- [提案] Classroom 用の Apps Script と同じプロジェクトで `GmailApp` を使う
  - 転送設定や Email Routing、Worker の `email` ハンドラは不要になる
  - Worker の CPU 10ms でメールをパースするリスクもなくなる
- [提案] ポータルはスクレイピングしない。通知メールがあれば Gmail 経由で拾い、なければ共有メニューで手動登録する

### #9 2026-10-11 [提案] WebClass は拡張(MV3)方式。優先度は低い

WebClass の通知メールは新しい課題や締切をカバーしないので、自動化するならログイン中のセッションを流用する拡張しかない。手動で困らなければ作らない。

### #10 2026-10-11 [本人] コンテキストはリポジトリの `ai-docs/` にコミットする

クラウドのエージェントも使うため。Claude Code のローカルのメモリ機能は使わない。決めたこと・学んだことは `ai-docs/` に書いてコミットする。
