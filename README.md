# myreminder

大学の課題のリマインダー。個人用。

締切から逆算して「いつまでに始めないと間に合わないか」を出し、すっぽかしと徹夜を防ぐ。課題にかける時間はなるべく増やさない。

## できること

- **登録**: 手入力が既定。AI で1行の文・告知文の貼り付け・スライドの写真から読み取ることもできる。Android の共有メニューからも送れる
- **繰り返し**: 毎週・隔週・毎月。回数・終了日・無期限
- **計画**: 時間割・予定・睡眠を除いた空き時間に課題を詰め、タスクごとの着手デッドラインと、週の山場(余裕が一番少ない締切)を出す。見積もりは実績から学習する
- **通知**: プッシュ(FCM)。朝・夜のまとめと、リスクに応じた個別の通知。授業中・作業中・睡眠中は保留してまとめる
- **ステータスと作業記録**: 「作業中」にした時間がそのまま実績になる
- **余裕リスト**: 急がないタスクを、今やると全体の余裕が増える順に並べる
- **ふりかえり**: 週ごとの作業時間、徹夜しなかった日数、見積もりの精度
- **取り込み**: Google Classroom の課題を Apps Script で取り込み、受信箱で承認してからタスクにする
- **Discord / Slack**: 提出したこと・1日の作業時間を投稿する。プッシュ通知を全部そのまま流すこともできる

## 仕組み

### 計画(`worker/src/planner/`)

時間割・予定・睡眠を引いた空き時間と、各タスクの残り作業から計画を立てる。すべて純粋関数で、vitest でテストしている。仕様は [ai-docs/specs/planner.md](ai-docs/specs/planner.md)。

**見積もりの較正(`estimate.ts`)**

自己申告の見積もりは楽観的になりがちなので(計画錯誤)、そのままは使わない。実績との比 `r = 実績 / 見積もり` を学習して補正する。

- `ln r` を正規分布とみなし、正規–逆χ²の共役事前分布でベイズ更新する。事前分布は `μ0 = ln 1.3`、`σ0 = 0.5`、`κ0 = ν0 = 3`
- 新しい実績ほど重く数える(半減期15件)。区分(種類 × 長さ)ごとの値は全体の値に縮小推定で寄せる(`k = 5`)ので、件数が少ない区分でも暴れない
- 計画に使うのは予測分布(Student-t)の 80% 点。t 分布の分位点は、正則化不完全ベータ関数を二分法で解いて求める
- 実績がない最初のうちは見積もりの約2倍で計画し、使うほど本人に合ってくる

**普段のキャパの学習(`usual-capacity.ts`)**

1日の作業時間の上限は決めない。代わりに「普段のキャパ」と「本気のキャパ」の2本を持つ。

- 普段のキャパ: 直近4週間のうち作業した日だけを見て、1日の作業時間の 75% 点を平日・休日別に取る。日数が少ないうちは初期値(平日 3h、休日 5h)に寄せる
- 本気のキャパ: 睡眠と予定を除いた空き時間すべて
- 睡眠時間帯はどちらにも入れないので、徹夜する計画は立たない

**締切ごとの余裕と着手デッドライン(`schedule.ts`)**

1. 需要上限テスト: 締切 `d_i` ごとに `s_i = 使える時間(今, d_i) − Σ{d_j ≤ d_i} 残りの作業(P80)` を計算する。普段・本気の両方で出す
2. 山場: 普段のキャパでの `s_i` が最小の締切。「10/13(火)・今週・余裕 1.5h」と出す
3. 配置: 締切が遅い順に、締切から逆向きに空き時間へ詰める(ALAP / EDF の逆回し)。最小の作業単位と公開日時を守る
4. 着手デッドライン: 配置した最初のブロックの開始時刻。「この時刻までに始めないと普段のペースでは収まらない」を、空き時間と必要時間の数字と一緒に出す。偽の早めの締切は作らない
5. リスク: 余裕・注意・危険・致命の4段階。普段のペースで間に合わなければ「本気が必要」、本気でも間に合わなければ致命
6. 捨てる候補: 本気のキャパでも足りないときは、Moore–Hodgson 法で「間に合わないタスクの数が最小になる外し方」を出す。手を抜くか延長を頼む候補として見せる

**余裕リスト(`slack-gain.ts`)**

急がないタスクを「次の空き時間(30〜90分)にやると、計画全体がどれだけ楽になるか」の順に並べる。

- 反実仮想の再計画: 「休んだ場合」と「そのタスクをやった場合」の2通りで計画し直し、差を辞書式で比べる。比べる順は、間に合わないタスクの数 → 山場の余裕 → 全体のストレス `Σ exp(−s_i / D / τ)`
- 無料プランの Workers は1リクエストの CPU が 10ms までなので、間に合わないタスクが0のときは配置を省き、需要上限テストだけを計算し直す近道を入れた。厳密な計算とランダムな400ケースで一致することをテストで確かめている。30タスク・120日で 9ms から 1.4ms になった

### AI(Workers AI)

AI は登録のときだけ使う。通知の送信(毎分の cron)では使わない。

- **文の解析**: 「情報倫理 来週月曜の授業前までにレポート2000字」のような1行や、告知文の貼り付けから課題を取り出す。時間割・科目・今の日時をプロンプトに渡すので、「授業前」は授業の開始時刻に、「来週月曜」は日付に解決される
  - モデル: `@cf/qwen/qwen3-30b-a3b-fp8`(1回 ≈16 neurons)。2回目は JSON Schema で出力の形を縛り、それでもだめなら `@cf/meta/llama-3.3-70b-instruct-fp8-fast` に切り替える
  - 出力は valibot で検証する。締切が読めない・過去の日付・確度が低い・「授業前」なのにその曜日に授業がない、のどれかなら「要確認」の印を付けて、理由と一緒に確認カードに出す
- **写真の解析**: スライドや掲示の写真から課題を読む。`@cf/google/gemma-4-26b-a4b-it` に画像を渡して1回で構造化し、予備は `@cf/qwen/qwen3.8-27b`。画像はブラウザで縮小してから送る
- **繰り返し**: 文に「毎週」「隔週」「毎月」とあれば読み取り、確認カードの既定値にする
- 解析の入力・出力・モデル・失敗はすべて `ai_log` に残す(写真は種類と大きさだけで、画像そのものは残さない)。無料枠(1日 10,000 neurons)に収まる

### 通知(`worker/src/notify/`)

- 送るのは切れ目(空き時間の始まり、授業が終わった直後、本人が決めた着手時刻)。授業中・作業中・睡眠中は保留し、明けたら1通にまとめる
- 基本は朝・夜のまとめ。個別の通知はリスクに応じて送り、致命以外は1日3件まで(設定で変えられる)
- 計画とは別に、締切の24時間前と3時間前には必ず送る(安全網)
- 文面は励ましや煽りを入れず、締切・必要な時間・着手の限界などの事実だけを並べる
- 毎時0分と、タスク・予定・設定が変わったときに、送る予定の通知を作り直す(冪等)

### 設計の根拠

先延ばしの研究を調べ、根拠の強さを確かめてから仕掛けを選んだ。詳細と出典は [ai-docs/research/behavior.md](ai-docs/research/behavior.md)。

| 使ったもの | 中身 |
|---|---|
| 実装意図(if-then プランニング) | 登録のときに「いつ始める?」を決め、その時刻に合図を1回送る |
| 計画錯誤・参照クラス予測 | 見積もりを自分の実績から補正する |
| 正直な締切 | 着手デッドラインは計算の根拠ごと見せる。偽の早めの締切は作らない |
| 時間の見せ方 | 締切は `10/14(水) 23:59 ・ 3日後 ・ 来週` と、曜日と相対表記を必ず付ける |
| 割り込みの研究 | 通知を切れ目に送り、まとめ、上限を設ける |

使わなかったもの: 外から押しつける中間締切(Ariely & Wertenbroch 2002 は 2026年9月に撤回された)、「未完了だと気になり続ける」という前提(ツァイガルニク効果はメタ分析で否定)、意志力の消耗を前提にした設計(36ラボの事前登録研究で d = 0.06)、ストリーク、損失を煽る文言。

## 構成

```
Android の PWA ─┐
Apps Script ───┼─ Cloudflare Access ─ Worker(Hono)─┬─ D1
               │                     ├ 静的アセット  ├─ Workers AI
               │                     └ /api/*       ├─ FCM
               │                                     └─ Discord / Slack
```

| ディレクトリ | 中身 |
|---|---|
| `worker/` | API・計画・通知(Cloudflare Workers + Hono + D1/drizzle + valibot)。cron は毎分 |
| `web/` | 画面(Vite + React 19 + Tailwind v4 + wouter)、PWA、FCM の Service Worker |
| `core/` | web と将来の RN アプリが共有する層(API クライアント、TanStack Query のフック、入力の変換・検証)。DOM を使わない |
| `gas/` | Classroom を取り込む Apps Script(TypeScript + esbuild。ビルドしてエディタに貼る) |
| `shared/` | biome の設定(submodule) |
| `docs/` | セットアップの手順 |
| `ai-docs/` | 計画書・決定ログ・仕様・調査メモ |

認証のコードはない。全体を Cloudflare Access の内側に置き、すべてのリクエストを同じ本人として扱う。

## 開発

pnpm 11(`package.json` の `devEngines`)と Node.js 22 以降。

```sh
git clone --recurse-submodules https://github.com/tomo-x7/myreminder
cd myreminder
pnpm install

# ローカルの D1 を作る
pnpm -F worker exec wrangler d1 migrations apply myreminder-db --local

# Worker は web/dist を配信するので、先に一度ビルドしておく
pnpm -F web build

pnpm worker dev   # http://localhost:8787
pnpm web dev      # http://localhost:5173(/api は 8787 へ)
```

Workers AI はローカルで動かないので、`wrangler dev` は Cloudflare へのログインが要る。AI の解析を使わないなら `pnpm -F worker exec wrangler dev --local` でよい。

```sh
pnpm check               # biome check --write
pnpm -F worker test      # vitest(計画・通知・取り込みなどの純粋関数)
pnpm -F worker typecheck
pnpm -F core typecheck
pnpm -F web build        # 型チェックとビルド
```

## デプロイ

`main` に push すると GitHub Actions が、チェック → web のビルド → D1 の migration → `wrangler deploy` を行う。初回の準備(Cloudflare・Access・Firebase・GitHub の secret)は [docs/setup-quick.md](docs/setup-quick.md)、詳しい手順は [docs/setup.md](docs/setup.md)。

秘密情報(Service Token、FCM のサービスアカウント、webhook の URL)はリポジトリに置かない。Worker の secret か D1 に入れる。
